# Poke Mover 代码分析

本文记录受支持原版二进制的流程分析，以及离线适配与原版的执行顺序对照。补丁的
构建方式和事务规则见 [`../README.zh-cn.md`](../README.zh-cn.md)。

## 目标与内存分布

- Title ID：`00040000000C9C00`
- 版本：v5.5.0
- 代码基址：`0x00100000`
- 解压代码 SHA-256：`001C20ADA74016507C969BB44A0A50F8EDF803EC06A3FC46834263BA8DF0FD2F`

| 区域 | 虚拟地址 | 属性 |
|---|---|---|
| `.text` | `0x00100000–0x0028E000` | 可读、可执行；实际内容结束于 `0x0028D1AC` |
| `.rodata` | `0x0028E000–0x002EC000` | 只读、不可执行 |
| `.data` | `0x002EC000–0x003293FC`，装载页延伸至 `0x0032A000` | 可读写 |
| `.bss` | 逻辑范围 `0x003293FC–0x003638A4` | 可读写、零初始化 |
| RW 页尾填充 | `0x003638A4–0x00364000` | 可读写、零初始化 |
| 线程栈 | 长度 `0x40000` | ExHeader 配置 |

ExHeader 声明的 `.text` 内容结束于 `0x0028D1AC`，最后一页映射结束于
`0x0028E000`。Ghidra 记录的最后指令/数据引用位置为 `0x0028D188`，最后函数结束于
`0x0028D18F`。页尾余量足够时，Luma 会在应用代码补丁之后，从声明的内容末尾安装
LayeredFS 荷载。本项目保留 `0x0028D1AC–0x0028D2DC` 的 `0x130` 字节不写入，
再将自身荷载起点对齐至 `0x0028D2E0`。已检查的 Luma 荷载为 `0x114` 字节；
以后若其增大，需要重新检查预留量。参见官方的
[安装逻辑](https://raw.githubusercontent.com/LumaTeam/Luma3DS/master/sysmodules/loader/source/patcher.c)
和[荷载汇编](https://raw.githubusercontent.com/LumaTeam/Luma3DS/master/sysmodules/loader/source/romfsredir.s)。

本项目尾部荷载可用区域为 `0x0028D2E0–0x0028DFC0`；末尾
`0x0028DFC0–0x0028E000` 的 `0x40` 字节保留给版本标识。内置第五世代来源
重定向接管原生卡带 I/O 钩子，不再为外部 Transporter Redirect Patch 保留
`0xE0` 区域；汇编区域边界与静态验证仍保护 Luma LayeredFS 和版本标识。
所有功能对象使用下面的新增页布局。加载器与票务测试策略共用环境判别函数；
后者还需单独检查票务接口响应，不能仅凭环境识别判定票务可用。

`0x00261C74–0x00262C10` 属于仍被调用的原版全局注册初始化函数，不能作为回收空洞。
启动流程进入 `0x00102ADC` 后，会遍历 `0x002EB744–0x002EBA58` 的 PREL32 构造表。
其中 `0x002EB7BC` 的表项存储 `0xFFF764B8`，与表项地址相加后得到 `0x00261C74`。
这个间接调用不会出现在直接分支或绝对指针搜索中。整个初始化函数与构造表都要求
与原镜像逐字节相同。原版票务作业和免费活动函数均不被回收。

| 荷载区域 | 内容 | 实际结束／余量 |
|---|---|---|
| text 页尾 `0x0028D2E0–0x0028DFC0`：已映射可执行填充 | 启动跳板与自动识别环境的 `code_expansion.o` | `0x0028D3C0`／`0xC00` 字节 |
| 新增页 `0x00365000–0x00368000`：扩展 data，启动后可执行 | 全部模式包装、原版跳板与功能对象 | `0x00367090`／`0xF70` 字节 |

启动钩子只在调用点 `0x00100010` 改为跳转到加载器。加载器保存 `r0–r12/LR`，
通过 SVC `0x27` 复制当前进程伪句柄取得真实句柄，使用 SVC `0x2A` 查询环境，
随后调用 SVC `0x70`（操作 `6`，
权限 `7`）启用新增三页的 RWX，关闭句柄并恢复寄存器，再以 Thumb 状态继续
`0x00102ADC` 的原构造函数遍历。实机失败以 SVC Break 中止；只有下面明确识别为
Azahar 的兼容情况，才允许未成功修改权限时继续。

配套 ExHeader 保持三个原段起点和 text／rodata 大小不变，仅把 data 扩到 `0x7C` 页
（末尾 `0x00368000`），将 BSS 大小设为 `0`，并在既有能力描述符中补所需的 SVC 位。
原 BSS 区域成为镜像中的零填充，其变量地址不移动；`0x00364000–0x00365000` 也是
零填充 RW 隔离页，而非未映射的保护页。本配置原先已授权 `0x23/0x27/0x2A/0x3C`，
实际只新增 `0x70`。
这借鉴了 [Magikoopa 的 data 尾扩容方式](https://github.com/RicBent/Magikoopa/blob/master/MagikoopaUI/patchmaker.cpp)，
但不将 text 实际大小扩至页边界，避免改变 Luma 的 LayeredFS 注入位置。
新增页最初由加载器作为 RW data 装入，SVC 仅改变这三页的权限，不会把旧 data/BSS
或整个进程全部改成可执行。

### BPS 通用装载与自动环境识别

BPS 的来源长度为 `0x22A000`，目标长度为 `0x268000`，元数据长度为 `0`。Luma 根据
扩容 ExHeader 提前分配目标缓冲；原版 Azahar 的 BPS 实现会先把镜像扩长到目标长度，
再还原补丁。两边得到相同字节，data 都映射至 `0x00368000`。原程序的 BSS 清零边界
`0x003293FC–0x003638A4` 不变。参见
[Luma 的 BPS 解码](https://github.com/LumaTeam/Luma3DS/blob/master/sysmodules/loader/source/bps_patcher.cpp)
和 [Azahar 的 BPS 扩长处理](https://github.com/azahar-emu/azahar/blob/9e6f523a57fac9564ac0bf8286db3c3702d301ec/src/core/file_sys/patch.cpp#L260-L280)。

只有 `GetSystemInfo(0x20000, 0)` 返回 `0`、输出低 32 位为 `2`、高 32 位为 `0`，才识别
为 Azahar。Luma 实机返回 `1`、输出 `0`，不会进入该分支。所有环境都会调用 SVC
`0x70`，返回 `0` 时正常成功；非零结果只有在已识别为 Azahar、且恰好等于输入的真实
进程句柄时才接受，对应未实现调用保留 `r0` 的行为。负值、其他正值、未知环境以及
句柄创建／关闭失败均按错误处理，并非忽略所有 SVC 错误。未实现 SVC 的模拟器仍
依赖宽松取指；已经实现时则正常执行权限修改。参考：
[Azahar 的身份查询](https://github.com/azahar-emu/azahar/blob/9e6f523a57fac9564ac0bf8286db3c3702d301ec/src/core/hle/kernel/svc.cpp#L1866-L1870)、
[未实现调用处理](https://github.com/azahar-emu/azahar/blob/9e6f523a57fac9564ac0bf8286db3c3702d301ec/src/core/hle/kernel/svc.cpp#L2440-L2448)
和 [Luma 实机查询](https://github.com/LumaTeam/Luma3DS/blob/master/k11_extension/source/svc/GetSystemInfo.c#L218-L222)。

票务模块仍采用 ARM；其他功能模块采用 Thumb。共用 TLS／SVC 原语保留为禁止内联的
ARM 函数，采用地址间接调用；ARM 分派通过 `BX/BLX` 明确切换状态，验证器会拒绝
目标文件导入器产生的不安全立即数 Thumb→ARM 调用。
卡带读写入口、列表虚表与来源选择处属于原址钩子；后续原版函数体由跳板继续
调用，不用于存放新代码。原版 data/BSS 地址不移动。

扫描器按需从原版堆分配 `0xE60` 字节上下文；指针使用 `0x00363FF0`，三个模式
字节使用 `0x00363FF4` 起的空间；`0x00363FF8` 保存本次票务作业的后端。这些地址位于逻辑 BSS 末尾 `0x003638A4`
之后、RW 页末尾 `0x00364000` 之前，不再使用原版 BSS 资源指针表中的
`0x00329FF8/0x00329FFC`。来源扫描不读取模式字节，由在线与离线两种模式共用。

四处票务钩子属于原址 `BL` 替换，仍占原来各 4 字节；其余票务状态和作业字节不变。

`.rodata`（`0x002EBA58–0x002EC000`，`0x5A8` 字节）和镜像中
`0x003293FC–0x0032A000` 的 `0xC04` 字节零填充不可执行；后者属于运行时逻辑
BSS 起始部分，不是空闲 data。静态零值不代表没有引用。
仅增大 ExHeader 的 `.text` 大小会与现有 `.rodata` 映射重叠。因此若要越过 `0x0028E000`
扩容，不能直接把 text 向后延伸。本 SVC 方案改为扩 data／物化 BSS，并使用配套
ExHeader、BPS 和启动权限修改，因此不需要对原程序整体重定位。

## 扩容方案的探索与对比

### 探索顺序

1. **参考 Magikoopa，实现实机扩容。** 将原 BSS 物化为零填充，扩展 data 装载页，
   在原 text 页尾放置启动加载器，再通过 SVC `0x70` 为新增页设置执行权限。
   原变量地址不动，不需要整体移动 rodata、data 或重定位原代码。初步版本使用 IPS；
   原版 Azahar 首先在补丁装载阶段失败，尚未执行到 SVC。参考
   [Magikoopa 的镜像与 ExHeader 修改](https://github.com/RicBent/Magikoopa/blob/master/MagikoopaUI/patchmaker.cpp)。
2. **补足自用模拟器的装载和 SVC 支持。**
   [`svc112` 分支](https://github.com/Wokann/azahar/tree/svc112) 做了两项不同的修复：
   [装载器](https://github.com/Wokann/azahar/blob/svc112/src/core/loader/ncch.cpp)
   根据完整段布局预分配镜像缓冲；
   [SVC 分派](https://github.com/Wokann/azahar/blob/svc112/src/core/hle/kernel/svc.cpp)
   与[进程内存实现](https://github.com/Wokann/azahar/blob/svc112/src/core/hle/kernel/process.cpp)
   接受真实进程句柄，执行本补丁所需的 Protect 操作并使代码缓存失效。
   这不是仅将返回值改成成功：前者使 IPS 能装入新增区域，后者实现权限修改。
3. **参考 OOT 项目的双布局，制作模拟器专用实验版。**
   [oot3d_practice_menu 的说明](https://github.com/gamestabled/oot3d_practice_menu/blob/master/README.md)
   为实机与 Citra 提供不同补丁及 ExHeader。它的
   [实机头部](https://github.com/gamestabled/oot3d_practice_menu/blob/master/exheader.bin)
   扩展 data、BSS 为零；
   [Citra 头部](https://github.com/gamestabled/oot3d_practice_menu/blob/master/exheader_citra.bin)
   则保留原 data、增大 BSS。本项目据此实验：原镜像 `0x22A000` 加上 `0x3D000` BSS，
   让旧模拟器的补丁缓冲达到 `0x267000`，并用当时的编译开关绕过权限修改。
   对方的[共用加载器](https://github.com/gamestabled/oot3d_practice_menu/blob/master/src/loader.c)
   仍调用 SVC `0x70`，但只把负值视为失败；未处理调用留下正句柄时也能继续。
   不能把这一点解释为 Citra 已实现了 SVC，或其编译宏取消了该调用。
4. **统一布局与发行文件，自动选择权限处理。** 最终改用 BPS 的目标长度重建镜像，
   不再依赖增大 BSS 来扩长模拟器缓冲。实机仍正常调用 SVC；已经实现 SVC 的 Azahar
   也正常修改权限；未实现的 Azahar 则仅在身份和返回值都符合上节条件时继续。
   删除旧的初始化区占用与实机／模拟器布局开关，所有环境使用相同 ExHeader 与荷载。

### 为什么早期方案不能互换

| 本项目方案 | 镜像装载方式 | 新增页执行方式 | 适用条件 |
|---|---|---|---|
| 初步实机方案，IPS | 扩展 data，BSS 为 `0` | 要求 SVC `0x70` 返回成功 | 实机或已修复装载器及 SVC 的 `svc112` |
| Citra 风格实验，IPS | 保留原 data，增大 BSS 来扩长模拟器缓冲 | 编译时绕过权限修改，依赖模拟器宽松取指 | 模拟器专用，不能套到实机 |
| 最终统一方案，BPS | 扩展 data，BSS 为 `0`；BPS 按目标长度重建 | 正常 SVC，或严格限定的 Azahar 未处理调用兼容 | 同一套文件用于实机与已测试的两类 Azahar |

这里有两道独立关卡。旧 Azahar
[装载器](https://github.com/azahar-emu/azahar/blob/9e6f523a57fac9564ac0bf8286db3c3702d301ec/src/core/loader/ncch.cpp)
在应用补丁前只按原代码长度加 BSS 扩长缓冲，不按新 data 页数补齐；其
[IPS 解码器](https://github.com/azahar-emu/azahar/blob/9e6f523a57fac9564ac0bf8286db3c3702d301ec/src/core/file_sys/patch.cpp)
遇到越界记录就失败。因此实机版的 BSS 为零时，会先出现“无法应用补丁”。即使绕过
装载问题，未实现的 SVC 也不会返回正常成功值，仍无法通过原先的严格启动检查。

反过来，[Luma 装载器](https://github.com/LumaTeam/Luma3DS/blob/master/sysmodules/loader/source/loader.c)
为代码补丁分配的缓冲来自 text／rodata／data 装载页，**不包含额外 BSS**。
仅增大 BSS 不能替实机 IPS 提供新增代码缓冲；BSS 也只是零初始化范围，不会把文件中
对应的荷载当作 data 内容装入。即便另行解决装载，实机仍需要真实的执行权限，不能
使用模拟器的绕过分支。这正是两个 ExHeader 不能互换的原因，而不是机器性能差异。

最终方案同时解决这两道关卡：BPS 负责完整目标镜像，扩展 data 的 ExHeader 负责映射，
启动加载器负责权限和环境判断。实机没有忽略错误；未实现 SVC 的 Azahar 兼容分支也
没有真正授予执行权限。详细返回值判断和内存边界见上节。

### 使用与方案定位

执行 `make -C mover` 后，将生成的 `code.bps`、`exheader.bin`、`romfs/` 成套安装。
实机使用 `SD:/luma/titles/00040000000C9C00/` 并启用 Luma 游戏补丁；Azahar 使用用户
目录的 `load/mods/00040000000C9C00/`，需完整 `0x800` 字节 ExHeader。移除同一目录的
旧 `code.ips` 和 `code.bin`，无需切换扩容宏或安装不同布局。票务策略独立控制是否允许
缺接口时的本地替代；测试策略复用环境判别函数，再检查票务响应，不以权限操作结果判断票务能力。

本项目新增的是“固定地址 data 尾扩容 + BPS 目标长度装载 + Azahar 身份与未处理 SVC
返回值识别”的**统一适配组合方案**，不是新的内核扩容原理。基础机制已有公开先例；
此次调研未能确认是否有完全相同组合的先例，故不宣称全球首创。其他项目的对比依据
是上述公开源码与 ExHeader 字段，并未在本轮运行它们。无 SVC 兼容仅针对已测试的
Azahar 行为，不承诺其他 Citra 分支或未来严格检查取指权限的模拟器；真正实现 SVC
的环境仍应使用正常成功路径。

## 共用 Bank 语言设置

两个调用点钩子让两种模式共用 SD 语言设置：

| 钩子 | 原操作 | 替换方式 |
|---|---|---|
| `0x00240D7C` | 创建启动界面前读取游戏数据 `+0xD0` 的缓存语言 | 从长度恰好为 `0x200` 的 `sav.bin` 读取语言字段，更新缓存语言与 `+0xD4` 汉字标志，再将所选 ID 返回 `r1` |
| `0x0025C618` | 原版语言确认回调重新绑定资源后调用 `LanguageSelection_SetSettings`（`0x0022C06C`） | 保留该 setter，再经 `sav.tmp` 更新已有 SD 记录 |

启动包装保留 `r0`、`r2`、`r3` 与返回地址。后续仍由原版 `0x0022AF28` 同时选择
消息资源和字库，并设置控制器的语言已就绪标志。文件缺失、不可读、长度错误或
语言 ID 不属于 `1/2/3/4/5/7/8/9/10` 时不改缓存设置，正常的主机语言／选择回退
仍可执行。日语显示偏好归一为布尔值。资源绑定函数和原版 setter 的函数体保持不变。

`language_settings.c/.h` 描述 Bank 序列化 `0x200` 字节记录中位于 `0x28` 和 `0x2A`
的两个 16 位字段。Bank 原版校验验证（`0x002CB920`）只覆盖 `0x00–0x1F`；
`0x002BAF38` 的校验更新采用相同输入，都不包含语言设置。Mover 更新只改动
`0x28–0x2B`，逐字节保留 `0x00–0x27` 与 `0x2C–0x1FF`，不重建事务元数据或重算校验。

启动只读取。确认选择时保留原版内存 setter，再读取完整已有文件；缺失或长度错误
的记录不创建、不替换。设置相同时不写入。更新复用 `readCompleteFile`、
`writeCompleteFile`、`openArchive`、`pathCommand`、`renamePath` 与 `closeArchive`。
顺序为删除旧 `sav.tmp`，写入／刷新／关闭完整临时记录，删除 `sav.bin`，然后改名。
读取、打开档案、删除临时文件或暂存写入失败均不会删除原文件；删除原文件失败
则不继续改名。最后改名失败时，完整临时记录留给 Bank 的现有缺文件恢复机制。
不打开 Bank 原存档档案，Bankdata 事务钩子也不参与这些语言操作。

## 票务状态与本地结果

原版票务状态为 `0x00249600`，局部子状态保存在状态对象 `+0x10`。两种模式都保留
该函数及回调 `0x0024991C`、清理 `0x00249CD8`，仅转接以下作业调用：

| 调用点 | 原函数 | 已选本地后端：离线，或测试策略 `1` 确认 Azahar 缺接口 | 已选原版后端：公开策略 `0`，或其他在线情况 |
|---|---|---|---|
| `0x00249754` | `0x0023D3C0` 初始化 | 填充本地作业字段，失败返回 `0` | 原调用及参数不变 |
| `0x00249774` | `0x0023E230` 轮询 | 返回完成并写成功结果 | 原调用及参数不变 |
| `0x00249818` | `0x0023BE4C` 免费活动请求 | 将本地窗口交给原版活动回调处理 | 原请求与异步回调不变 |
| `0x00249CEC` | `0x0023E63C` 解绑 | 未绑定客户端，返回后继续析构 | 原解绑不变 |

初始化包装保留作业 `r0`，从状态 `+0x28` 取共享数据作为 `r1`，以 `r2/r3` 传递
模式／策略，尾调用 C 后端选择器；其原版路线仍仅传作业给原版初始化函数。
后端只在初始化时确定一次，写入 `0x00363FF8`。轮询、活动和解绑包装只用易失寄存器
`r12` 读取这个标志；本地活动分支以状态对象作为 `r0`，原版分支保留原参数。
原 `BL` 返回地址、栈对齐与被调用者保存寄存器均保持。

| 子状态／节点 | 原版流程 | 本地结果流程 |
|---|---|---|
| `0` | 更新界面，等待下一阶段 | 不变 |
| `1` | 等待界面准备，分配并构造 `0x158` 字节作业，初始化客户端 | 保留等待、分配和构造，只替换客户端初始化 |
| `2` | 轮询作业；成功后计算期限、拷贝账户与购票次数、设置有效标志、注册活动回调 | 同一结果处理和注册流程，只替换轮询及活动请求 |
| `6` | 等待免费活动回调；回调转入 `3` | 本地窗口记录同步调用同一回调，由其转入 `3` |
| `3` | 检查期限与免费活动：可用转 `7`，不可用转 `4` | 同一判断；本地有效期限与免费标志转 `7` |
| `4/5` | 显示不可用提示并等待确认，随后进入错误退出 | 保留，不强行放行 |
| `7` | 设置完成阶段 `3`，返回成功退出 | 不变 |
| `8` | 设置错误阶段 `2`，返回结束 | 本地日期越界或分配失败也走此路线 |
| 清理 | 解绑、虚函数析构、清空作业指针、移除回调及释放活动资源 | 只免除未绑定客户端的解绑；其余仍执行原版 |

本地结果写入原作业，不直接覆盖共享数据中的期限结果：

| 作业字段 | 本地值及含义 |
|---|---|
| `+0xB8` 当前日期 | 主机当前时间，按原版 8 字节日期布局保存 |
| `+0x70` 到期日期 | 当前日期加 `999` 天，保留时分秒；不冒充当前时间 |
| `+0xB0` 账户字段 | 从共享数据 `+0x30` 保留现值，不生成账户编号 |
| `+0x78–0x8B` 五项购票次数 | `-1`，表示本地无购票历史 |
| `+0x04`、`+0xA0` | 系统商店结果、匹配目录数为 `0` |
| `+0xA4` 作业子状态 | 初始化 `0`，轮询成功后 `10` |
| `+0xA8/+0xA9/+0xAA` | 初次商店标志 `0`、期限已知 `0→1`、取消标志 `0` |
| SDK 指针、容器、字符串 | 保留原版构造值，不创建票务联网客户端 |

原版天数／小时数函数 `0x001DB83C`、`0x0023DFA8` 使用当前日期和到期日期，算出
`999` 天和总计 `23976` 小时；原状态回填共享数据 `+0x3C/+0x40`，并通过原版
有效性判断写入 `+0x44 = 1`，年度购票次数回填为 `-1`。本地活动结果将同一当前时间
至到期日窗口编码为原版 20 字节记录：4 字节保留字段、两个 7 字节日期、2 字节 CRC。
复用原 CRC 函数 `0x0019BD88` 和种子 `0xFFFF`，回调来源的请求标识匹配状态
`+0x44`，随后调用未修改的原版回调 `0x0024991C`。原回调继续检查请求标识、长度、
CRC 和包含边界的活动时段，计算剩余天数／小时数，并设置共享有效 `+0x44` 与免费
`+0x335` 标志。不发送请求，也不手动写入输出标志或剩余时间。
两边输入都是当前时间至 `999` 天后的窗口，仅使用各自原版处理所需的表示形式。
每次本地初始化均按主机时间重新生成，不采用固定的服务器活动日期。此过程不涉及
本地宝可里程，也不改变 Bankdata 事务或宝可梦检查。

公开发行时 `ONLINE_TICKET_CHECK_BYPASS` 设为 `0`：在线模式始终使用原版票务，接口缺失或检查
失败仍按原版处理，不提供伪造结果。策略 `1` 只允许已识别的 Azahar 做只读接口探测；
只有精确的未实现接口成功短响应，且临时句柄关闭成功时才选择本地结果。完整响应、
票据缺失、服务获取／传输错误或未知响应均保留原版。离线模式不受策略影响。
具体请求和响应判据见子项目 README；探测不新增 ExHeader 服务权限。

策略 `1` 只是作者测试用途，不是安全联网承诺。原版清理不将作业当前日期回填到
Bank 的共享日期／里程通路；下载回调 `0x0025C978` 载入服务器 Bankdata 主体与事务
描述，提交状态 `0x0024A0C4` 序列化该主体。未发现本地票务日期或使用权显示字段
写入主体的通路，但本地结果仍会改变使用权／活动判断，不替代 NNID、其他请求或
远端许可。公开版默认保持 `0`，缺接口时按原版报错，不使用本地结果继续真实联网。

### 第五世代游戏名按来源语言显示

## 逐槽传送判定

### 完整判定层次

一次传送并不是只执行一组“合法性检测”，而是依次经过四层：

1. 来源存档必须能正常读取并通过原版完整性检查；第五世代还会选择可用的冗余存档面。
2. 第五世代在线模式把 BOX1 的 30 条原始记录（含空槽）提交给远端服务；此时尚未执行
   14 项本地检查或传送格式转换。VC 则先转换候选。客户端验证响应后，取得与
   30 个槽位一一对应的 32 位结果码。该结果码表示通过、空槽／跳过、服务器拒绝，
   或要求修正昵称／原训练家名。服务器内部究竟执行了哪些检查并不存在于客户端代码中，
   客户端只负责消费这些结果码。
3. 远端结果允许继续处理的第五世代候选还要执行 14 项原版本地检查；VC 则使用另一条
   较短的本地判定链。
4. 通过的候选还要满足本地 `bankdata.bin` 有效且传送盒为空，才能写入传送盒。

第五世代已确认的远端结果语义为：`0` 表示允许继续，`20` 表示空槽，除 `20` 外非零且
小于 `250` 的值表示服务器拒绝，`250`、`251`、`252` 分别要求修正昵称、原训练家名或两者。
VC 使用 `0`、`20` 以及对应的名字修正码 `253`、`254`、`255`；其他非零结果会被拒绝。
因此这里的“远端信息”是逐槽判定码，不是另一份宝可梦数据，也不是第五世代 14 项本地
检查生成的失败位。

本次补丁只替代第 2 层在离线模式中无法取得的数组：第五世代只读检查记录完整性后，
有效空槽写入 `20`、非空候选写入 `0`、明确异常写入通用拒绝结果 `1`；VC 在先行
跳过空对象后把逐槽结果写为 `0`。第 1、3、4 层仍走原版流程。
所以离线模式仍会执行本地检测，但会失去仅由服务器提供的拒绝判定和名字修正。

### 第五世代的远端结果与本地结果

反编译函数 `0x002455D0` 的状态 4 会遍历 30 个固定 `0x88` 字节记录。共享流程对象
`+0x48` 保存逐槽的 32 位结果。主要分支可整理为以下等价伪代码：

```c
for (slot = 0; slot < 30; slot++) {
    result = slot_result[slot];

    if (result == 20)
        continue;                       // 原版空槽，不设置警告
    if (result != 0 && result < 250) {
        mark_remote_rejection();
        continue;
    }

    apply_known_remote_name_fixes(result); // 250、251、252
    failures = run_all_14_local_checks(candidate[slot]);
    handle_nonfatal_item_and_name_bits(&failures);

    if (failures == 0)
        convert_and_enqueue(candidate[slot]);
    else
        mark_local_rejection(failures);
}
```

14 项检查由 `0x002AFFE0` 的“函数地址 + 失败位”表驱动，全部执行后再合并处理，没有
遇到第一项失败便提前停止：

| 失败位 | 检查入口 | 实际本地检查 | 失败后的最终效果 | 本次补丁 |
|---:|---:|---|---|---|
| `0x0001` | `0x00242F8C` | 蛋标志必须关闭 | 致命；设置蛋类错误 | 不改 |
| `0x0002` | `0x00243028` | 酋雷姆不能是合体形态 | 致命；设置专用错误 | 不改 |
| `0x0004` | `0x00242FA0` | 是否携带道具 | 非致命；调用方清除此位，随后提示并移除道具 | 不改 |
| `0x0008` | `0x00243124` | 原训练家名检查位置 | **固定返回成功**：指令仅为 `r0=1; return`，不会本地产生失败 | 不改 |
| `0x0010` | `0x002432E0` | 昵称检查位置 | **固定返回成功**：指令仅为 `r0=1; return`，不会本地产生失败 | 不改 |
| `0x0020` | `0x00243050` | 物种与来源版本是否属于允许组合 | 致命；归入通用无法传送 | 不改 |
| `0x0040` | `0x0024320C` | 活动标志与指定来源训练家 ID 是否一致 | 致命；归入通用无法传送 | 不改 |
| `0x0080` | `0x002431FC` | 捕获／获得等级不能为零 | 致命；归入通用无法传送 | 不改 |
| `0x0100` | `0x002432E8` | 孵化地点、获得等级与来源世代的一致性 | 致命；归入通用无法传送 | 不改 |
| `0x0200` | `0x00243390` | 非孵化获得的记录不得低于物种最低捕获等级 | 致命；归入通用无法传送 | 不改 |

| `0x2000` | `0x00243318` | 旧来源版本不能带有不相容的隐藏特性标志 | 致命；归入通用无法传送 | 不改 |

调用方会显式清除 `0x0004`、`0x0008`、`0x0010` 三个位：携带道具会被移除；两项
名字位预留了修正分支，但对应的本地检查函数固定成功，因此正常情况下不会由本地链
触发。在线模式中，远端结果 `250` 表示修正昵称、`251` 表示修正原训练家名、`252`
表示两者都修正；这些是独立于两项固定成功本地函数的远端行为。

### VC 的本地判定

VC 使用反编译函数 `0x002463D8`，没有调用上面的 14 项表。其顺序可整理为：

```c
for (slot = 0; slot < 30; slot++) {
    if (converted_candidate_is_null(slot))
        continue;
    if (source_had_item[slot]) {
        mark_item_rejection();
        continue;
    }
    if (source_was_egg[slot]) {
        mark_egg_rejection();
        continue;
    }

    result = slot_result[slot];
    if (result == 20)
        continue;
    if (result != 0 && result != 253 && result != 254 && result != 255) {
        mark_remote_rejection();
        continue;
    }
    if (result == 254 || result == 255)
        normalize_original_trainer_name();
    if (result == 253 || result == 255)
        normalize_nickname();
    enqueue_converted_candidate(slot);
}
```

因此，VC 在本地明确检查的是空对象、携带道具和蛋；更广泛的合法性判定及 `253–255`
名字修正码来自远端。它不会执行第五世代的 14 项本地表。

### 本次补丁实际调整的位置

在线模式会提交 30 个候选，验证返回签名后覆盖完整逐槽结果数组。来源记录访问函数
`0x0019A6D8` 直接定位选中的存档保存面及 BOX1，不规范化空记录。`0x002B3FD4` 是
原版成功传送后清除来源槽时使用的写入模板，不能作为所有输入空槽的唯一判据。

第五世代离线适配在原请求点 `0x00245728` 完成以下只读分类：

1. 保留此前的原版整份存档校验和冗余保存面选择。候选来源不可用时设置读取错误
   子状态 `13`，从 `0x00246368` 返回本帧；随后由原版错误提示、等待确认及退出路径
   处理，不进入逐槽转换。
2. 按原版记录头读取 PID、控制标志、校验和及 64 个 16 位记录体字。控制标志带
   原版排除位 `0x04` 时写入拒绝结果 `1`。
3. 按控制位 `0x02` 判断记录体是否已经解码。未解码时以头部校验和值为种子，逐字
   执行 `seed = seed * 0x41C64E6D + 0x6073`（32 位回绕），再异或 `seed >> 16`。
   解码仅使用临时值，不改写来源记录、控制标志或校验和。
4. 解码字之和的低 16 位必须与记录头校验和一致，否则写入拒绝结果 `1`。这项记录
   校验与整份存档块校验相互独立，不重新计算后覆盖来源校验值。
5. 使用 `(PID >> 13) & 31` 和原版 `0x002B42E4` 分块排列表定位种族。校验正常且
   种族为 `0` 时写入 `20`；种族为 `1–649` 时写入 `0`；其余种族写入 `1`。不要求
   空槽其余字段全零或匹配模板，不提前对空槽执行等级、语言、来源版本或名字规则。
6. 成功覆盖全部 30 项结果后，从 `0x00245800` 接回原版本地链。`1` 只作为本地
   通用拒绝值使用，不表示已复刻某个服务器专属错误码或完整合法性算法。

### 在线与离线的执行顺序对照

| 顺序 | 第五世代在线模式 | 第五世代离线模式 |
|---|---|---|
| 读取来源 | 原版读取、存档块校验、冗余保存面选择 | 保持不变 |
| 准备 30 槽 | 取得并复制原始 `0x88` 字节记录，包含空槽 | 从同一缓冲区只读检查完整性和种族 |
| 获取逐槽结果 | 发出远端请求，等待并验证响应，取得 30 项结果 | 本地填入 `0`、`20` 或 `1`；整体读取失败进入原版错误链 |
| 开始后处理 | 清除内存候选槽、警告和来源槽映射 | 接回同一原版入口 |
| 消费结果 | `20` 无警告跳过；拒绝值设置警告；允许值继续 | 使用同一分支 |
| 准备非空候选 | 复制记录到临时副本，处理远端名字修正，并确保解码和分块定位 | 原版复制、解码和定位不变；不生成名字修正码 |
| 本地判定 | 执行全部 14 项检查，合并并处理失败位 | 保持不变，见上方完整检测表 |
| 转换及入盒 | 通过者转换后加入内存传送盒，记录对应来源槽 | 保持不变 |
| 确认及保存 | 显示警告与确认，随后执行原版保存事务 | 保持现有本地 bankdata 保存事务，不由分类器修改来源记录 |

分类结果 `0` 只表示允许继续本地检查，不表示已经允许传送。被前置或本地检查拒绝
的记录不会进入成功候选映射；“无法传送”是从本次候选列表排除，不是清空来源槽。
只有成功候选在后续确认传送流程中由原版来源游戏保存逻辑处理。

其他适配保持如下：

- 在 VC 远端请求点 `0x002460B8`，离线模式把 30 项结果全部写为 `0`，然后从
  `0x002461D0` 继续。VC 已经先跳过空对象，所以不需要伪造结果 `20`。
- 每次进入离线路径都覆盖全部 30 项，防止从标题切换模式后继承同一进程中在线模式
  留下的结果。
- 在线模式仍从两个钩子返回原始远端请求流程；14 个第五世代检查函数、失败位后处理、
  VC 的空对象／道具／蛋判断及候选写入均未修改。

离线模式保留全部原版本地检查，并补足可在本地确定的记录完整性与空槽分类；它不
复现未知的服务器专属拒绝规则或名字修正。清除离线会话残留的远端事务参数属于状态
隔离，不是宝可梦合法性检测。

## BankObject 与 bankdata

Mover Bank 对象虚表：`0x002E6DD0`。文件内容对应对象 `+8`，固定长度 `0xBB518`。

| 虚表偏移 | 地址 | 功能 |
|---:|---:|---|
| `+0x08` | `0x0025AE44` | 序列化完整文件 |
| `+0x0C` | `0x0024D868` | 载入完整文件 |
| `+0x10` | `0x0025AE38` | 返回 `0xBB518` |
| `+0x18` | `0x0024D898` | 载入 `0xACA48` 旧格式并升级 |
| `+0x1C` | `0x0025AE20` | 检查 `u16(data+0x15C)==2` |

Mover 和 Bank 使用相同的完整文件格式。程序识别的当前格式长度为 `0xBB518`、版本为 `2`、盒数为 `100`。

### Transfer Box

| 文件偏移 | 长度 | 内容 |
|---:|---:|---|
| `0x0AAF14` | `30 × 0xE8` | 30 个传送槽主体 |
| `0x0AD5FC` | `30` | 30 个并行标签 |

| 地址 | 功能 |
|---:|---|
| `0x0019A224` | 载入一个传送槽及标签 |
| `0x0019A6F4` | 写入记录和标签并执行原程序规范化 |
| `0x0019A7E0` | 清空槽和标签 |
| `0x0019A858` | 判断槽是否含有效记录 |
| `0x0024D624` | 统计 30 个有效槽 |

传送区未发现单独的服务器记录 ID 或签名生成函数。原程序同时处理 `0xE8` 槽主体和 1 字节标签；`0x0025C978` 的处理顺序为备份候选槽、载入完整对象、在下载 Transfer Box 为空时恢复候选槽。

## 保存

`0x0024A0C4` 序列化完整 `0xBB518` 对象后执行远端更新、卡带保存和提交/回滚。

| 地址 | 原程序行为 |
|---:|---|
| `0x0024A240` | 发起远端暂存并等待异步结果 |
| `0x0024A3E4` | 卡带保存成功后发起远端提交 |
| `0x0024A420` | 卡带保存失败后发起远端回滚 |

三处分支均通过异步完成标志推进外层状态机。Mover 序列化和上传的是与 Bank 相同的完整文件格式。
